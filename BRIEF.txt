## Environment Safety
- APP_DEBUG must only be true when APP_URL is a genuine local dev address
  (http://localhost, http://127.0.0.1, or a *.test/*.localhost domain such as
  Laragon's auto-generated http://counselstone.test). Never pair APP_DEBUG=true
  with a real/deployed APP_URL — visitors would see full stack traces on error.
- AppServiceProvider::preventDebugModeOnNonLocalUrl() forces debug off as a
  safety net if this is ever misconfigured, but .env should be set correctly
  regardless — don't rely on the safety net.
- APP_ENV should be "local" for dev, "production" for a real deploy. LOG_LEVEL
  should drop from "debug" to something quieter (e.g. "error") in production.
- The seeded director account (database/seeders/DatabaseSeeder.php) generates
  a random password printed once to the console on `db:seed` — it is not
  stored anywhere, so copy it immediately and change it after first login.

## Roles
Four roles in ascending permission order:

- **solicitor** — sees all matters by default, but a `SCOPE_SOLICITORS` config flag
  exists (default false) to restrict to assigned matters only — switch on without
  a rebuild when needed. No financials, no locked/director_only content.
- **accounts** — payment plans, instalments, chase logs, Xero integration only.
  No case notes, no director_only content.
- **admin** — day to day management: clients, leads, documents, matters.
  Cannot delete or edit locked records. Cannot see director_only content.
- **director** — full access to everything. Only role that can lock records,
  unlock records, and see director_only flagged content. Cannot be restricted.

## Locking & Director-Only Fields
Add to any table that needs protection:
- `locked` (bool, default false) — when true, only director can edit or delete
- `director_only` (bool, default false) — when true, only director can see

Apply this pattern to canEdit() / canDelete() on every Filament resource:

```php
public static function canEdit(Model $record): bool
{
    if ($record->locked) {
        return auth()->user()->hasRole('director');
    }
    return auth()->user()->hasAnyRole(['director', 'admin']);
}

public static function canDelete(Model $record): bool
{
    if ($record->locked) {
        return auth()->user()->hasRole('director');
    }
    return auth()->user()->hasAnyRole(['director', 'admin']);
}
```

## Payment Chase Logic
Daily scheduled job checks all instalments where due_date has passed and paid_at is null:
- 3 days overdue → chase email step 1 (friendly reminder)
- 7 days overdue → chase email step 2 (firmer tone)
- 14 days overdue → SMS step 1
- 21 days overdue → SMS step 2 + set matter status to suspended + notify director
- Xero webhook confirms payment → set paid_at, set status to paid, cancel pending chase steps
- Log every chase action in chase_logs
- Never send a chase step that has already been logged for that instalment

## Lead Nurture Logic
- Lead created → send acknowledgement email immediately (step 0)
- 48hrs no response → follow up email (step 1)
- 5 days no response → SMS nudge (step 2)
- 10 days no response → final email, mark status as lost (step 3)
- Lead responds at any point → pause sequence, flag for manual follow up
- Converted leads → cancel all pending nurture sequences

## Client Portal (Phase 2 — schema built, UI deferred)
- Separate auth guard at /portal
- Clients see: matter status, court date, payment plan, instalments, documents where visible_to_client=true, messages
- Clients can: upload documents, reply to messages, complete their own profile, write client statement
- Clients cannot see: internal notes, director_only content, suspended status reason, other clients

## Audit Logging
- Uses spatie/laravel-activitylog (polymorphic activity_log table), not a
  bespoke per-model audit table — the earlier TimeEntry-only
  time_entry_audits/TimeEntryAudit mechanism was removed in favour of this.
- Model side: add `LogsActivity` + `App\Concerns\HasReasonedActivityLog`
  traits, then define `getActivitylogOptions()` (see TimeEntry/
  PrecedentTemplate for the pattern: useLogName(), logFillable(),
  logOnlyDirty(), dontSubmitEmptyLogs()). useLogName() must match the tab key
  used in ListAuditLog::getTabs().
- Filament side, for a full Resource Edit page: add
  App\Filament\Concerns\RequiresChangeReasonOnEdit to the Edit page class,
  and add ::changeReasonField() to the resource's form schema. For a
  relation-manager modal EditAction instead, add
  App\Filament\Support\ChangeReasonField::make() to its form and override
  EditAction::using() to call $record->updateWithReason($data, $reason)
  (see TimeEntryRelationManager). The reason field only appears/requires on
  the edit operation, never create.
- Creation and deletion are logged automatically with no reason required —
  only edits require one.
- Browsing the log: app/Filament/Admin/Resources/AuditLog (nav group
  "Audit Log", director-only via canAccess()). Add a new tab in
  ListAuditLog::getTabs() per newly-audited resource.
