# Kaselog full application audit — 2026-08-06

Audit-only pass (no fixes applied), triaged for the pre-demo/pre-go-live window. Severity labels:
- **confirmed-live-breaking** — verified to break, by running code or by an unambiguous vendor-code path
- **confirmed-lower-impact** — verified real by code reading/tests, but bounded blast radius
- **theoretical-needs-verification** — plausible from code reading; one targeted test would settle it

The two highest-priority items in the whole report are **F1 (ProcessXeroPayment crash — verified by running the job under queue-worker conditions)** and **F2 (all staff locked out of the admin panel the moment `APP_ENV` isn't `local` — i.e. on the production deploy)**. Fix those two before anything else.

## Area 2 — Tenant isolation

### F1. `ProcessXeroPayment` eager-loads tenant-scoped relations before tenant context exists → job crashes; suspended matters never reactivate — **confirmed-live-breaking**

- **Where:** `app/Jobs/ProcessXeroPayment.php:38-42` (the `->with('paymentPlan.matter')`), crash at `:100` (`$instalment->paymentPlan->matter` in `reactivateMatterIfSuspended()`).
- **What:** The instalment lookup correctly uses `allTenants()`, but the `with('paymentPlan.matter')` eager loads run in the same query pipeline — and eager loads go through the *related* models' own `TenantScope`. In a fresh queue worker `CurrentTenant` is null, the scope fails closed (`1 = 0`), and `paymentPlan` is cached on the model as **null** even though the row exists. `CurrentTenant::set($instalment->tenant)` on line 50 comes too late — the null relation is already cached.
- **Consequence:** The instalment **is** marked paid (instance `update()` bypasses global scopes), then the job throws `Attempt to read property "matter" on null`. Pending chase-log cancellation and — critically — **suspended-matter reactivation never run**, and the job lands in `failed_jobs`. On retry it early-returns ("already marked paid"), so the reactivation is lost permanently. Every real Xero payment webhook hits this path.
- **How verified:** Wrote a throwaway feature test simulating a fresh queue worker (`CurrentTenant::clear()` then `handle()`): it crashed with exactly `Attempt to read property "matter" on null`. Test deleted after verification.
- **Why tests didn't catch it:** There are no tests for this job at all (see Area 6), and any test written naturally would have had a tenant already set from fixture setup — masking it.
- **Suggested fix:** Follow the established pattern in `SummarizeMatterDocument` (the working twin of this job): fetch the bare instalment via `allTenants()` with **no** eager loads, `CurrentTenant::set($instalment->tenant)`, *then* `$instalment->load('paymentPlan.matter')`. Add a job test that runs with no ambient tenant.

### F2 → filed under Area 3 (it's an auth finding) but flagged here because it's the other go-live blocker.

### F3. `AuditLogResource` resolves tenant via `Filament::getTenant()` instead of `CurrentTenant` — **confirmed-lower-impact** (divergent-twin)

- **Where:** `app/Filament/Admin/Resources/AuditLog/AuditLogResource.php:59-66`.
- **What:** Every other tenant-scoped query in the app resolves through `CurrentTenant::id()` (which itself falls back to `Filament::getTenant()`). This resource re-implements resolution directly against the Filament facade — a third resolution path, exactly the `get()`/`id()` class of quiet divergence this audit was commissioned for. Today the two agree inside a panel request; they stop agreeing the moment anything calls `CurrentTenant::set()` during an admin request (as webhooks/jobs already do elsewhere).
- **How verified:** Code reading; behaviour currently correct (it is fail-closed).
- **Suggested fix:** Swap to `CurrentTenant::id()` so there is exactly one resolution order app-wide.

### F4. Tenant-scoping mechanics elsewhere — **verified clean**

- All 17 `BelongsToTenant` models checked; `inheritsTenantIdFrom()` chains are complete and consistent (incl. the new `document_ai_summaries` → `matterDocument`, `quill_conversations` → `matter`, `quill_messages` → `quillConversation`).
- All `withoutGlobalScopes()`/`withoutGlobalScope()` uses audited: every one either strips only `ExcludeConvertedLeadsScope` (keeping tenant scope intact) or is the sanctioned `allTenants()` escape hatch, used only in: director-only `AllTenantsOverview` widget, per-tenant job loops, `Matter::generateReference` (explicitly re-filters `tenant_id`), and the two webhook-driven jobs. The one *unsafe* use is F1 above — not the bypass itself but what happens next to it.
- `ProcessLeadNurture` / `ProcessPaymentChases` / `RetellWebhookController` all set/restore tenant context correctly (set → try → finally restore), and their eager loads happen *after* the set — only `ProcessXeroPayment` got the order wrong.
- Portal ownership checks: `MatterView` enforces tenant scope + `client_id` ownership; `SetPortalPassword` enforces tenant scope + token↔matter↔client consistency. The portal blade exposes only reference/status/court date — no Documents, Time Entries, or Finance are client-visible anywhere yet, and `visible_to_client` is not yet load-bearing.
- `RetellWebhookController` with an unmapped `agent_id` logs the payload with `tenant_id = NULL` — intentional (`retell_call_logs.tenant_id` is deliberately nullable) and skips business processing. Fine.

## Area 3 — Auth & authorization

### F2. Staff `User` model doesn't implement `FilamentUser` → **every staff login gets 403 in production** — **confirmed-live-breaking on deploy**

- **Where:** `app/Models/User.php` (implements `HasTenants` but not `Filament\Models\Contracts\FilamentUser`); enforcement at `vendor/filament/filament/src/Http/Middleware/Authenticate.php:33-39`.
- **What:** Filament's auth middleware: if the user model isn't a `FilamentUser`, access is allowed **only when `config('app.env') === 'local'`**. This machine runs `APP_ENV=local`, so everything works in every local click-test — and breaks with a blanket 403 for all staff the moment the app is deployed with `APP_ENV=production`. The `Client` model implements the contract correctly; `User` is its divergent twin.
- **How verified:** Vendor middleware read directly (Filament v5); `User` confirmed by reading the model. Not run live (needs a production env flip).
- **Suggested fix:** `User implements FilamentUser` with `canAccessPanel(Panel $panel): bool` — at minimum `return $panel->getId() === 'admin';`. Then a smoke test that boots with `app.env=production` and asserts a staff login reaches the dashboard (this exact class of local-only bug is invisible to the current suite).

### F5. `portal_enabled` and `locked` on Client are never enforced — disabling a client's portal access doesn't actually revoke anything — **confirmed-lower-impact** (arguably higher)

- **Where:** `app/Models/Client.php:68-71` (`canAccessPanel` returns true unconditionally for the portal panel); `app/Filament/Portal/Pages/PortalLogin.php` (no check); grep confirms `portal_enabled` is only ever *displayed/edited* in admin (`ClientForm`, `ClientsTable`, infolist) and *set* by `SetPortalPassword`.
- **What:** The admin UI presents `portal_enabled` as a toggle (and `locked` as a director control), implying staff can cut off a client's portal access. Nothing on the auth path reads either flag: a client with a password can keep logging in and viewing their matter after staff switch `portal_enabled` off.
- **How verified:** Code reading + exhaustive grep of both flags' read sites.
- **Suggested fix:** Enforce in `Client::canAccessPanel()` (`return $panel->getId() === 'portal' && $this->portal_enabled && ! $this->locked;`) — Filament checks it on every authenticated portal request, which also kills existing sessions, not just new logins. Add portal feature tests for both flags.

### F6. `PrecedentTemplateResource` has no `canAccess()`/`canEdit()` gating — **confirmed-lower-impact** (same category as the Audit Log incident)

- **Where:** `app/Filament/Admin/Resources/PrecedentTemplates/PrecedentTemplateResource.php` — only `canDelete()` (director) is defined.
- **What:** Every other resource declares `canAccess()` against a role list; this one silently inherits "everyone". Any authenticated staff role — including `accounts` — can view, create, and edit the firm's precedent templates (which feed generated client-facing documents, so an edit has real consequences). Built without a gate and, per the pattern named in the brief, likely never click-tested per-role.
- **How verified:** Code reading against the established pattern in the other five resources.
- **Suggested fix:** Decide the intended roles (probably director/admin/solicitor like Matters) and add `canAccess`/`canCreate`/`canEdit` accordingly.

### F7. `TimeEntryResource::canAccess()` returns bare `true` — needs-decision

- **Where:** `app/Filament/Admin/Resources/TimeEntries/TimeEntryResource.php:52-55`.
- **What:** Diverges from every sibling's `hasAnyRole([...])` shape. Plausibly deliberate (accounts need read access for billing; `canCreate`/`canEdit`/`canDelete` are individually gated) but it's undocumented and indistinguishable from an omission. If deliberate, a one-line comment ends the ambiguity; if not, gate it.

### F8. Guest/signed-URL routes — **verified clean**

- Exactly two guest-reachable portal routes exist: `/login` and `/{tenant}/set-password/{token}`. Set-password has `signed` middleware (expiry enforced — the URL is generated with `temporarySignedRoute`, 72h default), plus single-use via `portal_token` regeneration-on-reissue and null-out on success, plus tenant-scoped token+matter+ownership cross-checks. No other guest route needs these protections.

### F9. Guard isolation — **verified clean by design, untested** (see Area 6)

- `web` guard → `users` provider; `portal` guard → `clients` provider; disjoint tables, each panel authenticates only its own guard, `Client::canAccessPanel` pins clients to the portal panel, and (post-F2 fix) `User::canAccessPanel` should pin staff to admin. A portal session cannot satisfy admin's `Authenticate` middleware or vice versa. No test asserts this today.

## Area 1 — Routing

### F10. The known catch-all collisions — **verified fixed, live**

Ran the real route matcher over the risk URLs (`Route::getRoutes()->match(...)` in tinker):
`/up` → health route; `/admin` → admin tenant redirect; `/admin/{slug}` → admin dashboard (portal excluded by the `(?!admin)` constraint); `/admin/{slug}/clients` → clients index; `/livewire-*/livewire.js` → Livewire asset; `/filament/exports/1/download` → Filament export; `/{slug}/{ref}` → portal matter-view; `/{slug}/set-password/{t}` → portal set-password. All four `{tenant}`-shaped routes are confirmed flagged `isFallback` (including `filament.portal.home`, which Filament flags itself). `favicon.ico`/`robots.txt` exist in `public/` so they're served by the web server and never reach the portal catch-all.

### F11. Bare tenant URL `/{slug}` for a logged-in client likely 500s — **theoretical-needs-verification**

- **Where:** `filament.portal.home` → `vendor/.../RedirectToHomeController` → `Panel::getRedirectUrl()` (`vendor/filament/filament/src/Panel/Concerns/HasRoutes.php:200-248`) → first navigation item's `getUrl()`.
- **What:** For an authenticated client, the redirect target is the first navigation item's URL. `MatterView` inherits `$shouldRegisterNavigation = true` and its route requires `{reference}` — generating its nav URL without a reference should throw `UrlGenerationException` (500). Guests are fine (redirected to login before this code runs). Clients can plausibly reach the bare URL by trimming their bookmarked matter URL.
- **How to verify:** One click-test: log in as a client, visit `/{tenant-slug}` with no reference.
- **Suggested fix:** `protected static bool $shouldRegisterNavigation = false;` on `MatterView` (it's not a navigable page), and decide where the bare tenant URL should land (probably the client's own matter, or a 404).

### F12. No reserved-slug validation for tenants — **theoretical-needs-verification**

A tenant whose slug equals a literal top-level route prefix (`storage`, `filament`, `webhooks`, `retell`, `up`, `login`, `logout`, `livewire-*`) would have all its portal URLs shadowed by those exact-match routes — the mirror image of the original collision bug (this time the literal route wins, correctly, and the tenant loses). `admin` is already excluded from *matching*, but nothing stops any of these being *created* as a slug (tenants are seeded/manual today, so low likelihood). Suggested fix: a reserved-slug validation rule wherever tenants get created/edited, sharing one reserved list with `excludeAdminPathFromTenantSlugMatching`.

### F13. `getByName()` audit — **clean**

No remaining `getByName` call sites (only the explanatory comment in `AppServiceProvider`). All name-based lookups left in the app are runtime `route()`/`getUrl()` calls, which are safe: Laravel's `RouteServiceProvider` refreshes name lookups in a `booted()` callback, so post-boot name resolution sees Filament's late-applied names.

## Area 4 — AI/Prism integration

### F14. Failure-mode handling — **verified clean** (code reading; "unreachable" previously live-tested)

- `SummarizeMatterDocument`: connect-refused/timeout (Guzzle exceptions), malformed/unparseable structured output (Prism throws) all funnel through `catch (Throwable)` → `Failed` + user-facing message; missing/corrupt file lands in `PdfTextExtractionService`'s `catch (Throwable) → null` → clean `Failed`. `failed()` hook re-derives tenant context correctly for the catastrophic path. Missing keys in the structured payload are defended with `?? ''`/`?? []`.
- `QuillChat`: same `catch (Throwable)` → `Failed` message row; `connect_timeout 5` prevents hangs.
- Minor: a missing/corrupt PDF reports the "no extractable text / scanned document" message — slightly misleading but graceful.
- Minor: `app/Livewire/QuillChat.php:105-115` — the withMessages/withPrompt explanation comment is duplicated verbatim (copy-paste artifact).

### F15. Prism `withMessages()`/`withPrompt()` conflict class — **clean elsewhere**

Only three Prism call sites exist: `QuillChat` (fixed, `withMessages` only), `DocumentSummaryService` (`withPrompt` only), `AiTestCommand` (`withPrompt` only). No other instance of the conflict.

### F16. AI tables tenant scoping — **verified clean** (see F4). One note: `QuillChat`'s Livewire update requests depend on Filament's persistent tenant middleware for scope resolution — this is the live-tested multi-turn path, so it demonstrably works; just be aware the chat's tenant context comes from a different mechanism than first page load.

### F17. Deployment/ops notes for the AI features — needs-decision before go-live

- `QUEUE_CONNECTION=database`: if no queue worker runs on the production host, every summary sits at "Processing…" forever (the UI polls at 4s with no timeout state). Worth a deploy-checklist line, and possibly a "stuck > N minutes → Failed" sweep later.
- `QuillChat` is synchronous with a 90s Guzzle timeout — on Windows PHP counts wall-clock toward `max_execution_time`, and production web servers/proxies often cap request time below 90s. A slow (not failed) Ollama generation could 500/504 mid-request instead of hitting the graceful path.

## Area 5 — Divergent-twin pattern

(F2 `User` vs `Client`, F3 `AuditLogResource` vs `CurrentTenant`, and F1 `ProcessXeroPayment` vs `SummarizeMatterDocument` are the three biggest twins — filed above.)

### F18. `StatsOverview` "Overdue Instalments" count ignores `director_only`; `OverdueInstalmentsWidget` filters it — **confirmed-lower-impact**

- **Where:** `app/Filament/Admin/Widgets/StatsOverview.php:29-38` (no filter) vs `app/Filament/Admin/Widgets/OverdueInstalmentsWidget.php:24-35` (`whereHas('paymentPlan.matter', director_only = false)`).
- **What:** A non-director admin sees a stat count that includes director-only matters' instalments while the adjacent table excludes them — numbers disagree on the same dashboard, and the count leaks the *existence* of director-only overdue instalments. Same divergence pattern for the other three stats, which *do* filter — the first stat is the odd one out.
- **Suggested fix:** Add the same `whereHas` filter to the stat (or deliberately document that money totals are unfiltered).

### F19. Generated documents merge global firm contact details with per-tenant legal identity — **confirmed-lower-impact** (multi-brand correctness)

- **Where:** `app/Services/DocumentGenerationService.php:70-78`; `config/kaselog.php` (whose own comment says legal identity moved per-tenant).
- **What:** `firm_name` / `company_number` / `sra_number` correctly resolve via `Tenant::legalEntity()`, but `firm_address` / `firm_phone` / `firm_email` still come from global env config — the second brand's generated documents will carry the first brand's contact details. Half-migrated twin of the tenant-branding work.
- **Suggested fix:** Move address/phone/email onto the tenant (or its legal entity) alongside the other fields.

### F20. `director_only` on a Client doesn't cascade to that client's matters — needs-decision

A non-director can't open a director-only client's record (`ClientResource::canView`), but that client's *matters* remain fully visible (with the client's name on them) unless each matter is individually flagged `director_only`. If the intent of flagging a client is confidentiality of the relationship, this is a hole; if matter-level flagging is the intended unit, it's fine. Flag for the client conversation, not a code fix yet.

### F21. Activity-log tenant stamping is a trap for future models — advisory

`activity_log.tenant_id` is only populated via `HasReasonedActivityLog::tapActivity()`. The only two `LogsActivity` models today both use the concern, so all current rows are stamped — but any future model adding `LogsActivity` without `HasReasonedActivityLog` writes NULL-tenant rows that silently never appear in the (tenant-scoped, fail-closed) Audit Log UI. Worth a comment on the concern or a test asserting every `LogsActivity` model also uses the concern.

### F22. Small twins, minor

- `Matter::generateReference` has a read-then-increment race (two concurrent creates → duplicate reference → unique-index violation on the second). Low likelihood at this firm's volume.
- "Days overdue" is computed independently in three places (`OverdueInstalmentsWidget`, `ProcessPaymentChases`, `Instalment::getDisplayStatusAttribute`) — consistent today, unguarded tomorrow.

## Area 6 — Test coverage gaps (flagged only, not built)

The suite (44 tests, all green) is strong exactly where tonight's bugs already were, and absent where this audit found new ones:

1. **No tests for the three scheduled/webhook-driven jobs** (`ProcessXeroPayment`, `ProcessPaymentChases`, `ProcessLeadNurture`) — the code that hand-manages tenant context outside request scope, and where F1 (confirmed crash) lives. Priority: a per-job test that runs with **no ambient tenant** (the F1 reproduction is a ready-made template — see the deleted `TempXeroAuditVerificationTest` shape in this audit's history).
2. **Zero portal feature tests.** MatterView ownership + cross-tenant 404s, SetPortalPassword signature/expiry/single-use/reissue-invalidation, and the F5 flags are all live-tested only. These are the client-facing security boundary — highest-value new tests after (1).
3. **Guard isolation untested** — one test each way (portal session → admin route → redirected; staff session → portal matter URL → redirected).
4. **No production-env test.** F2 is invisible to the entire suite because everything runs `APP_ENV=testing`/`local`. One smoke test flipping `config(['app.env' => 'production'])` around a panel request would have caught it and will catch regressions of the fix.
5. **Two-tenant rigor exists only in `ClientResourceTenantScopingTest`.** The Retell webhook tests are single-tenant — notably no test that a phone number existing in *both* tenants attaches the call note to the right one (the exact cross-match risk the controller's own comment warns about).
6. **`SetsUpTenant` masks missing-tenant bugs by design** — every test starts with a tenant set, which is why F1 could never surface. Job/webhook tests specifically should start from `CurrentTenant::clear()`.
